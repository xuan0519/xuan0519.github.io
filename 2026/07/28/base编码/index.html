Chapter1：认识base编码

Base 编码（如 Base64、Base32、Base16 等）是一类用于将任意二进制数据转换为纯文本字符串的编码方式。

在计算机中，许多网络协议（如邮件、URL、HTTP 协议头）最初都是为传输 ASCII 文本设计的。如果直接传输图片、音视频等二进制文件，遇到不可见字符或控制字符时，数据很容易丢失或损坏。Base 编码就是为了解决这个问题而诞生的。

核心误区提醒： Base 编码不是加密算法！它的映射表是公开的，任何人都能直接解码。它的作用是保证数据传输的可靠性，而非安全性。

但需注意， Base 编码会使文件体积变大

在 Base64 中，原本 3 字节（24 bits）的数据变成了 4 个 Base64 字符（对应 4 字节），所以体积会增加约 33%。

在 Base32 中，每 5 字节变 8 个字符，体积增加约 60%。

在 Base16 中，每 1 字节（8 bits）变 2 个字符（Hex），体积翻倍（增加 100%）。

Chapter2: Base的各种编码类型

Base16

Base16（也常被称为十六进制编码 / Hex Encoding）是最基础、最直观的二进制到文本的编码方式。

它的核心逻辑非常简单：用 16 个打印字符来表示所有数值。因为计算机中的 1 个字节（Byte）包含 8 个比特（Bit），正好可以完美拆分为两个 4-bit 的半字节（Nibble），而每个 4-bit 的取值范围恰好是 0~15，完全可以用 16 个字符一一对应。

Base32

Base32 是一种将二进制数据转换为 32 个可打印 ASCII 字符组成的文本编码格式（RFC 4648）。

与 Base64 相比，Base32 设计的核心目标是防误读和不区分大小写，特别适合需要人工抄写、口述或在不区分大小写的文件系统中使用的场景。

最常用的标准 Base32 字符集由 大写英文字母 A-Z 和 数字 2-7 组成（共 32 个）：

为什么排除数字 0, 1, 8, 9？

  • 0 和 O 极其容易混淆。
  • 1、I 和 l 极其容易混淆。
  • 剔除了 0, 1, 8, 9 后，剩下的数字正好是 2-7，加上 26 个字母恰好凑齐 32 个字符。

工作原理

Base32 的基本逻辑是按 5 bits 为一组进行切分（因为2的5次为32）

  1. 组合： 将输入的二进制数据按 5 个字节（40 bits） 分为一组（40 是 8 bit 字节和 5 bit 编码的最小公倍数）。
  2. 拆分： 把 40 bits 拆分成 8 个 5-bit 的半字节。
  3. 查表： 将每个 5-bit 的十进制数值（0 ~ 31）映射到 Base32 索引表对应的字符。

补位机制

如果输入的数据字节数不能被 5 整除，末尾会用 0 补足 5 的倍数个 bit，并在生成的字符串末尾加上 = 作为填充标示。一个完整的 Base32 编码块长度必须是 8 的倍数：

原始字节数 编码后字符数 末尾填充 = 数量
1 字节 (8 bits) 2 个字符 ====== (6 个)
2 字节 (16 bits) 4 个字符 ==== (4 个)
3 字节 (24 bits) 5 个字符 === (3 个)
4 字节 (32 bits) 7 个字符 = (1 个)
5 字节 (40 bits) 8 个字符 无 (0 个)

虽然 Base32 的体积膨胀率约 60%（比 Base64 的 33% 稍高），但它在以下领域非常流行：

  1. 双因素认证（2FA / TOTP 密钥）： Google Authenticator 或 Microsoft Authenticator 绑定时提示输入的密钥（如 JBSWY3DPEHPK3PXP）就是 Base32 编码，极易人工输入且不易看错。
  2. 暗网 / 洋葱路由地址（.onion）： Tor 网络的 V3 域名（如 v3...onion）就是公钥信息的 Base32 编码。
  3. DNS 记录与文件名： 域名和某些操作系统文件名对大小写不敏感，Base32 不区分大小写的特性非常适合这些场景。

Base58

Base58 是一种专门为人类友好和高容错率设计的文本编码方式。

它最初由中本聪（Satoshi Nakamoto）为比特币（Bitcoin）设计，目的是生成便于人工抄写、展示且不易出错的加密货币钱包地址。

字符集：去粗取精

Base58 是在标准 Base64 字符集的基础上，剔除了 6 个极易混淆或影响选中的字符：

Base58 在比特币地址生成中的应用流程
  1. 0（数字零）和 O（大写字母 O）—— 极易看错。
  2. I（大写字母 I）和 l（小写字母 L）—— 在很多等宽字体中完全一样。
  3. +（加号）和 /（斜杠）—— 在双击选中文本时，这两个符号会导致选区断开，影响复制粘贴。

工作原理：大数进制转换

与 Base64、Base32 或 Base16 不同，Base58 无法直接按固定 bit 位拆分。

它的底层机制是将整个二进制字节串视为一个超大整数，然后进行进制转换：

  1. 转为大整数： 将输入的二进制字节数组看作一个大整数 N。
  2. 不断模 58： 将 N连续除以 58，每次计算得到的余数（0 到 57）映射到 Base58 字符表中。
  3. 反转拼接： 将每次得到的字符按从后往前的顺序拼接，生成最终的 Base58 字符串。
  4. 前导零处理： 原始数据开头的每一个 0x00 字节，都会在 Base58 编码结果开头直接补充一个字符 1。

扩展衍生：Base58Check

在区块链领域（如 BTC、LTC 等），更常用的是 Base58Check。它在 Base58 的基础上加入了校验码机制：
$$
\text{数据结构} = \text{前缀（1字节）} + \text{有效载荷 (Payload)} + \text{双重 SHA-256 校验码前4字节}
$$

  • 作用： 如果用户在输入钱包地址时打错了一个字符，钱包客户端可以通过校验码瞬间检测出地址无效，从而防止资产转错到黑洞地址。

Base64(important)

Base64 是全网最常用、最普及的二进制文本编码格式（RFC 4648）。

它的核心作用是将任意二进制数据转换为 64 个安全且可打印的 ASCII 字符，以便在网络传输（如 HTTP、SMTP 邮件）中安全通过，防止数据因不可见字符或控制字符被丢弃或转码损坏。

字符集与映射机制

标准 Base64 使用以下 64 个字符（不含填充符）：

  • 大写字母 A-Z（26 个，索引 0–25）
  • 小写字母 a-z（26 个，索引 26–51）
  • 数字 0-9（10 个，索引 52–61）
  • 特殊符号 + 和 /（2 个，索引 62 和 63）

拆分与填充原理（3 字节变 4 字符）

因为 2^6 = 64，Base64 选择将二进制数据按 6 bits 为一组切分（原本 1 字节为 8 bits）。

最小公倍数是 24 bits：因此 3 个输入字节（24 bits）会被恰好重新分组为 4 个 6-bit 字符。

  • 完整 3 字节（如 "Man"）：
    $$
    8 bits × 3 = 24 bits \rightarrow 拆分为 6 bits × 4 \rightarrow 编码为 TWFu
    $$

  • 不足 3 字节时的补位（Padding）：

    • 若剩下 2 字节（16 bits）：补零到 18 bits，拆成 3 个字符，末尾补 1 个 =。
    • 若剩下 1 字节（8 bits）：补零到 12 bits，拆成 2 个字符，末尾补 2 个 =。
（直接粘贴一个csdn帖子的图片实例，这样更好理解qwq）

衍生版本：URL-Safe Base64

由于标准 Base64 包含 + 和 /，如果直接放进 URL 的 query 参数中，+ 会被解读为空格，/ 会被解读为路径分隔符。

为了解决这个问题，诞生了 URL 安全的 Base64：

  • 将 + 替换为 - (减号)
  • 将 / 替换为 _ (下划线)
  • 通常移除末尾的 =

常见于 JWT（JSON Web Token）和 OAuth Token 中。

常见应用场景

  1. Data URI 内嵌文件： 在 HTML/CSS 中直接嵌入小图片，减少 HTTP 请求。

  2. 电子邮件附件（MIME 标准）： 保证邮件服务商传输图片、文档等二进制内容时不乱码。

  3. 身份认证令牌（JWT）： Token 的 Header 和 Payload 都是用 URL-safe Base64 编码呈现。

Base85

Base85（也称为 Ascii85）是一种效率极高、空间利用率极优的二进制文本编码格式。

它的设计初衷是在保持文本安全传输的前提下，解决 Base64 体积膨胀过大的问题（Base64 体积膨胀约 33%，而 Base85 仅膨胀 25%）。

为什么是 85？数学原理

Base85 的核心逻辑是将 4 个字节（32 bits） 数据编码为 5 个 85 进制字符：

  • $$
    2^{32} = 4,294,967,296（4 字节所能表达的最大数值状态数）
    $$

  • $$
    85^5 = 4,437,053,125
    $$

因为 85^5 > 2^{32}，所以用 5 个 85 进制字符足以无损表达任何 32 bit（4 字节） 的二进制数值。

相比之下，Base64 是用 4 个字符表达 3 字节数据（膨胀率为
$$
4/3 \approx 133.3%
$$
），而 Base85 是用 5 个字符表达 4 字节数据（膨胀率为
$$
5/4 = 125%
$$
），节省了更多带宽和空间。

两种主流变体与字符集

Base85 在历史演进中形成了两个最著名的版本：

1. Adobe Ascii85（PostScript / PDF 标准）

  • 字符集： 从 ASCII 码 33 (!) 到 ASCII 码 117 (u) 的 85 个可打印字符。
  • 特殊优化（全零压缩）： 如果连续遇到 4 个全零字节（0x00000000），不需要输出 5 个字符，而是直接用单个字符 z 替代。这在文本或图片含有大量空白字节时能极大缩小体积。
  • 包裹界定符： 编码结果通常以 <~ 开头，以 ~> 结尾。

2. RFC 1924 / z85（Git / IPv6 标准）

  • 字符集： 删除了引号、斜杠等容易被代码或 Shell 转义干扰的特殊符号，改用数字 0-9、字母 a-z / A-Z 以及一些安全符号（如 .-:+=^!/*?&<>()[]{}@%#）。
  • 应用场景： RFC 1924 最初被提出用来以更短的文本表达 IPv6 地址；后来的 Z85（ZeroMQ）变体被广泛用于二进制协议和 Git 的内部存储。

Base91

Base91 是一种将二进制数据转换为 8 bit ASCII 文本的高效率编码方式，由 Joachim Henke 设计。

它是目前在仅使用单字节 ASCII 字符的前提下，压缩效率最高、体积膨胀率最低的常用文本编码之一（体积膨胀率仅为 14% ~ 23%，远优于 Base64 的 33.3% 和 Base85 的 25%）。

核心原理：动态变长 Bit 映射

与 Base64（固定 6 bits）、Base32（固定 5 bits）或 Base85（固定 32 bits 转 5 字符）不同，Base91 的最大特色是采用了变长分组算法：

  1. 变长比特积攒： Base91 维护一个位缓冲区（Bit Buffer）。它每次从输入流中打包 13 bits 或 14 bits 数据。

  2. 巧妙的数学边界：

    • $$
      91^2 = 8281
      $$

    • $$
      2^{13} = 8192 （可装下 13 bits）
      $$

    • $$
      2^{14} = 16384
      $$

    • 如果积攒的数据组合值小于 8192，则一次性编码 13 bits（输出 2 个 Base91 字符）；如果大于等于 8192，则一次性编码 14 bits（同样输出 2 个 Base91 字符）。

  3. 极极致利用： 这种根据数据内容动态选择 13 bits 还是 14 bits 的机制，使得 Base91 能够将 ASCII 字符集利用到极致。

字符集：利用全部安全 ASCII 字符

标准 ASCII 码中共有 94 个可打印字符（ASCII 33 到 126）。Base91 剔除了其中 3 个在代码或传输中容易引起转义麻烦的字符（例如双引号 ", 反斜线 \, 以及短划线 - 或换行符等特殊处理），精选出 91 个安全字符：

Base100

Base100是一种非常独特的 Emoji 表情符号编码。

与常见的 Base64 或 Base16（Hex）不同，Base100 不是为了提高传输效率而设计的，它的核心玩点在于将任意二进制数据或文本全部转换为 Emoji 表情串。

核心原理：

$$
1 字节 \rightarrow1 个 Emoji
$$

在计算机中，1 个字节（Byte）的取值范围是 0 ~ 255（共 256 种可能）。

Base100 的做法是：将每个字节的数值加上一个固定偏移量（通常偏移 55 或映射到特定的 UTF-8/Unicode Emoji 区块），转换为 1 个 4-bit 长度的 UTF-8 表情符号。

例如：

  • 文本 "the quick brown fox..."
  • 经过 Base100 编码后会变成：👫👟👜🐗👨👬👠👚👢🐗...

工作机制举例

以字符 'A'（ASCII 码 65）为例：

  1. 原始数值：65 (Hex: 0x41)
  2. 加上 Base100 的 Base 偏移：$65 + 55 = 120$
  3. 组合 UTF-8 编码字节：最终映射到 Unicode 的 Emoji 区块（如 U+1F400 系列，包含 👝, 👛, 👜, 👟 等日常物品与人物 Emoji）
  4. 输出：对应的 Emoji 表情

特性与优缺点对比

优点
  1. 视觉直观极强： 编码结果是一串纯 Emoji 表情，极具趣味性。
  2. 校验方便（对人类友好）： 比起一长串复杂的十六进制 Hash 值，人类对图片/Emoji 的视觉记忆更敏感，一眼就能看出变化。
  3. 字符数变少： 如果按 Unicode 字符数量计算，1 字节对应 1 个 Emoji 字符，在限制字符数（而非字节数）的平台上有特殊用途。
缺点

  1. 数据体积巨大（膨胀率高达 ~200% - 300%）：

    因为一个标准的 UTF-8 Emoji 表情在底层通常占用 4 个字节（Bytes），而它表达的其实只有 1 个原始字节。因此文件实际占用的磁盘/网络流量会膨胀约 3 到 4 倍。

典型应用场景

  • CTF 隐写与极客 Challenge： 网络安全竞赛（CTF）中常出现用 Base100 隐藏加密 Payload 或 Flag 的题目。
  • 终端校验码展示： 在 CLI 命令行工具里，把 Hash 或 Checksum 转为一行 Emoji，方便开发人员快速比对。
  • 趣味聊天 / 社交媒体发文： 隐藏文本内容，看似是一串无意义的表情包，解码后才是真实留言。

Chapter3: 编码之间的互相转化

Base 家族（Base16, Base32, Base58, Base64, Base85, Base91, Base100 等）之间的互相转换，本质上从来都不是“直译”，而是以“原始二进制数据（Raw Bytes）”作为桥梁的二次转换过程。

无论你想把 Base64 转成 Base58，还是把 Hex (Base16) 转成 Base32，核心流转模型永远是：
$$
\text{源 Base 文本} \xrightarrow[\text{第一步}]{\text{解码 (Decode)}} \mathbf{\text{原始二进制数据 (Bytes)}} \xrightarrow[\text{第二步}]{\text{编码 (Encode)}} \text{目标 Base 文本}
$$

转换逻辑示意

假设我们要把 Base64 的字符串 "SGk="（英文 “Hi”）转换为 Base16 (Hex)：

  1. 第一步（解码）： 将 Base64 的 "SGk=" 解码，还原出它背后的原始二进制字节 b'Hi'（即 Hex 内存中的 0x48 0x69）。
  2. 第二步（编码）： 将获得的字节 b'Hi' 传入 Base16 编码器，得到目标字符串 "4869"。

关键提醒： 永远不要尝试写正则表达式或硬映射表去把 Base64 的字符直接映射到 Base32，因为不同 Base 算法的切分 Bit 位数（4 bits、5 bits、6 bits、85 进制等）完全不同，只有**二进制字节（Bytes）**才是所有 Base 编码通用的“度量衡”。

互转时的注意事项与坑点

  1. 补位符（Padding =）补全： 在处理 Base64 或 Base32 字符串时，如果输入的字符串丢失了末尾的 =（被裁剪了），大多数解码器会直接报错。在解码前可能需要补齐字符串长度到 4 或 8 的倍数。
  2. 大小写敏感性：
    • Base16 / Base32： 规范默认不区分大小写（但解码库通常要求大写）。
    • Base58 / Base64 / Base85： 严格区分大小写，打错一个字母大小写就会导致整个原始数据损坏。
  3. 字符集变体（如 URL-Safe Base64）： 如果你要把一个 URL-Safe Base64（含 - 和 _）转成其他 Base，需要先将其中的 - 换回 +，_ 换回 /，再进行标准 Base64 解码。
